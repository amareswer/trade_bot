**What happened:** a user-visible BTC rally (roughly $90k → $108k CAD, 2026-08-14 through
2026-08-24) had the crypto bot sitting flat the whole time. Investigation traced a genuine raw
BUY signal on **2026-08-18 12:00 UTC** (Mode B breakout, RSI=70.0, ADX=23.16, price≈$90,042)
that never became a fill — `logs/trades.db`'s last fill of any kind was 2026-06-30, seven weeks
earlier.

**Why:** confirm whether the bot was actually watching the market and correctly declined to
trade, or whether something silently dropped a real signal — this distinction matters a lot for
trusting the system going forward, and the investigation itself exposed that the pipeline had no
way to answer it with certainty at the time (see "the diagnostic gap" below).

**How to apply:** if a future "why didn't the bot buy X" question comes up, check
`logs/live_signals.csv` first (persistent, not log-rotated) — every BUY the pipeline ever
considered-but-blocked is a row there, with the specific gate. If the gate label is `mtf_trend`,
`external_signal`, or `regime` (post-2026-08-24 logging fix — see below), that's now
distinguishable directly from the CSV/log; before that fix, all three collapsed into one
`"regime"` label with no way to tell them apart.

## The investigation (2026-08-24, read-only)

**Direct evidence, not inference:** `logs/live_signals.csv` (a persistent CSV, unaffected by log
rotation — written every time a BUY is considered but blocked, an existing mechanism) had the
exact row:

```
2026-08-18 12:00,BTC/CAD,90042.4,70.0,23.16,0.5433,BULLISH,BUY,regime,HOLD
```

`blocked_gate=regime` — but at the time, that label was shared by **three different mechanisms**
in `bot/main.py`: the MTF (multi-timeframe) daily-trend gate, the external Fear&Greed gate, and
the regime-proper (ADX/EMA-spread) gate. The ADX/spread values on this row (23.16 / 0.5433%)
clear the live thresholds (18.0 / 0.4%) comfortably, ruling out regime-proper directly.

**Pinned down by direct recomputation:** replayed the exact same daily-trend calculation
(`trend()`, 9/21 EMA crossover) the live MTF gate uses, on real Kraken 1D BTC/CAD closes through
2026-08-17 (excluding the still-forming 08-18 daily candle — matching the live code's `[:-1]`
slice exactly). Result: **BEARISH.** This matches the MTF gate's exact trigger condition
(`if _mtf_trend == "BEARISH": raw_signal = Signal.HOLD`).

**Conclusion: the MTF daily-trend gate correctly vetoed this BUY.** The 4h chart had just
flipped bullish (a fast breakout); the daily chart's slower EMA crossover hadn't caught up yet.
This is the gate doing exactly what its own code comment says it exists to do — not a bug, not a
downtime gap, not a silently-dropped signal. Bot uptime around 08-18 was independently confirmed
via `logs/shadow_report_2026081{4..9}.md` (daily shadow-signal reports with zero gaps 08-01
through 08-23, only generated by the bot's own live scheduler) and the 08-18 16:06 UTC report's
own text ("235 CANDLE entries found", 100% match rate, 0 mismatches vs. a fresh stateless
replay) — strong evidence the bot was alive and internally consistent that day.

**Capital ($77 slot cap) was not the cause** — the signal never reached sizing (blocked earlier
in the pipeline) — but is worth recording: at $90,042/BTC, `calc_trade_qty($77, $90042)` =
0.000086 BTC (~$7.74 notional), a genuinely thin margin against typical exchange minimums.
Already covered by the existing pre-trade min-size guard (`LiveExecutor`, added 2026-07-30,
Telegram-alerts without blocking).

## The diagnostic gap this investigation had to work around, and the fix (2026-08-24)

Tracing the full pipeline (`logger.info("CANDLE...")` → strategy-internal gates → MTF → external
→ regime-proper → correlation → candle watchdog → state machine → capital pool → RiskManager's 7
checks → executor) found:

- **Every gate logged rejections, but none logged passes** — the only way to know a gate ran and
  didn't block anything was absence of a rejection line, which is indistinguishable from "this
  gate never ran at all."
- **`RiskManager.evaluate()`'s all 7 checks (HALT, KILL_SWITCH, MAX_DRAWDOWN, WEEKLY_LOSS,
  DAILY_TRADE_CAP, DAILY_LOSS, POSITION_SIZE) had zero `logger` calls inside the function at
  all** — rejections were only visible via the caller's single summary line (whichever
  `block_reason` "won"), with no way to tell which check actually fired from logs alone.
- **MTF gate, external (Fear&Greed) gate, and regime-proper gate shared one `"regime"` label** —
  exactly the ambiguity this investigation had to resolve by independently recomputing the MTF
  daily trend from scratch, rather than reading it directly.
- **Capital/sizing decisions (requested qty vs. cash available vs. final qty) were computed but
  never logged** — only the final `trade_qty` number silently flowed forward.
- **A genuinely unhandled exception from `LiveExecutor.execute()` had no guaranteed Telegram
  alert** — `execute()` catches many *specific* known failure modes internally, but has no
  top-level catch-all; anything outside those specific try/except windows could propagate
  uncaught from the call site in `bot/main.py`.

**Fixed, same day — pure logging/alerting additions, no logic/threshold/behavior change:**
1. `mtf_trend` and `external_signal` split out of the shared `"regime"` label (regime-proper
   keeps `"regime"` — it already had both pass and fail logging before this fix, e.g. `REGIME
   GATE [%s]: OK ADX=... spread=...`, so it needed no other change).
2. Every gate in the traced pipeline (strategy-internal handoff, MTF, external, correlation,
   candle watchdog, state machine, capital pool) now logs on both pass and reject, not just
   reject.
3. `RiskManager.evaluate()` now logs each of the 7 checks by name on rejection
   (`RiskManager REJECT [sym]: <CHECK> — <message>`) and logs once on full approval for BUY
   signals specifically (`RiskManager APPROVE [sym]: all 7 checks passed`) — SELL/HOLD approvals
   are not logged to avoid flooding (SELL fires on every exit, HOLD on every idle tick).
4. Capital-sizing now logs requested qty, sizing method (notional vs. ATR-risk-capped), cash
   available, max affordable, and final qty — one line, BUY signals only.
5. The primary strategy-signal `executor.execute()` call site (`bot/main.py`, the traced
   pipeline's endpoint) is now wrapped in a try/except that logs and Telegram-alerts
   (`alerter.error`) on any unhandled exception, then degrades to "no order this tick" instead of
   crashing the loop or going unnoticed. **Not applied** to the two other `execute()` call sites
   in `bot/main.py` (partial-TP fill, urgent SL/TP exit) — same theoretical gap exists there,
   flagged but deliberately out of scope here (this investigation traced the entry pipeline, not
   the exit paths, and exit-path behavior changes deserve their own separate review).

**Verification:** full test suite **629 passed**, unchanged count (pure logging additions, no
new test scenarios required — existing `test_risk_manager.py`'s 32 cases already exercise all 7
checks and the approve path, and all still pass, confirming no return-value/logic change).
`bot/strategy/*` untouched (`git diff --stat` empty), `build_indicator_config()` untouched,
strategy hash `b30f2f9e769c8d41` confirmed unchanged. Manually verified every new log line
formats correctly (no %-substitution crashes) via a direct `RiskManager.evaluate()` smoke test
covering DAILY_TRADE_CAP/HALT/POSITION_SIZE rejects and the APPROVE path.
